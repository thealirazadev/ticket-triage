# Contributing to ticket-triage

Thanks for your interest in improving ticket-triage. This document covers the
local setup, the checks every change must pass, the migration workflow, and what
a pull request is expected to contain.

By participating you agree to abide by the [Code of Conduct](CODE_OF_CONDUCT.md).

## Prerequisites

- Python 3.12 (the project pins `>=3.12,<3.13`).
- [`uv`](https://docs.astral.sh/uv/) for dependency and environment management.

No LLM provider key is needed to develop or run the tests: the provider is
mocked (see [Tests](#tests)).

## Setup

```bash
uv sync                      # install exactly what uv.lock pins
cp .env.example .env         # optional; every setting has a default
uv run alembic upgrade head  # create the SQLite schema and seed routing rules
```

`.env` is git-ignored. You only need to fill in `LLM_API_KEY`, `LLM_BASE_URL`,
and `LLM_MODEL` if you want to run triage against a real provider; the tests and
the offline demo never require them.

## Checks

Run all three before opening a pull request; CI runs the same commands and will
fail the PR otherwise.

```bash
uv run ruff check .          # lint (E, F, I, UP, B)
uv run black --check .       # format check; run `uv run black .` to apply
uv run pytest                # full suite
```

Ruff and Black are both configured for a 100-column line length in
`pyproject.toml`; do not reformat with different settings.

## Tests

The suite makes **zero network calls and needs no secrets**. The single provider
integration (`app/services/llm_client.py`) is exercised through
`httpx.MockTransport`, wired up by the fixtures in `tests/conftest.py`. Each test
runs against a fresh temporary SQLite database created by `alembic upgrade head`,
so migrations, CHECK constraints, and seed data are genuinely exercised rather
than mocked away.

When you change behavior, add a test that fails before your change and passes
after it. Put provider-shaped responses behind the mock transport; never call a
real provider API from a test.

## Database migrations

Every schema change ships as a new Alembic migration; **applied migrations are
never edited afterward.** Migrations live in `migrations/versions/` and use
sequential numeric revision ids (`0001`, `0002`, ...), not autogenerated hashes.

To add one:

1. Create the next file, e.g. `migrations/versions/0003_short_description.py`,
   following the shape of the existing migrations (`revision`/`down_revision`
   set to the sequential ids, an `upgrade()` and a matching `downgrade()`).
2. Keep the model definitions in `app/models.py` in sync with the migration.
3. Apply and verify it round-trips:

   ```bash
   uv run alembic upgrade head
   uv run alembic downgrade -1
   uv run alembic upgrade head
   ```

`env.py` reads the database URL from `DATABASE_URL` (via `Settings`), so the same
migration runs against SQLite in development and Postgres in production.

## Pull requests

- **One discrete change per commit** (a migration, a model, a route, a service,
  its test), each in a working state. Do not bundle a whole feature into one
  commit.
- Use short, imperative, conventional commit messages, for example
  `fix: handle empty cart` or `test: cover breaker recovery`. No emoji.
- Make sure `ruff`, `black --check`, and `pytest` are all green locally.
- Describe what changed and why in the PR body, and fill in the checklist in the
  pull request template.
- Never commit secrets. Keep `.env.example` current (dummy values only) if you
  add a new setting.

## Security

Please report suspected vulnerabilities privately as described in
[SECURITY.md](SECURITY.md), not through public issues or pull requests.
